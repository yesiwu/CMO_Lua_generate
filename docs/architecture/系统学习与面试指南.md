# CMO Lua Agent：系统学习与面试指南

> 适用对象：需要快速理解项目、准备项目介绍或技术面试的开发者。
> 阅读原则：先记住“谁负责决策、谁负责确定性执行、谁保存事实”，再进入具体实现。

## 1. 一句话介绍

这是一个把军事场景 JSON 转换为可执行 CMO Lua、运行仿真、评估候选策略、沉淀经验并支持多代训练的 Agent 系统。

它的核心设计不是“让 LLM 直接写 Lua 并相信结果”，而是：**LLM 只提出受约束的结构化决策；Python 确定性代码负责校验、渲染、执行、持久化和恢复。**

因此，系统既支持交互式 JSON→Lua 工作流，也支持用户一句话启动、后台持续运行、可以查询/暂停/恢复的多代训练。训练过程中出现异常时，轻量 Recovery Harness 会先区分网络临时故障、Lua/CMO 领域故障、Python 代码故障和未知故障，再决定重试、调用既有领域修复、进入受控源码修复或停止。

## 2. 先建立整体心智模型

系统有两条正式主链：

```text
普通场景链：
JSON 场景 → 校验 → 场景 IR/策略契约 → 数据库解析 → Manifest → Lua 生成与预检

长期训练链：
用户训练请求 → TrainingService → 后台 Runner → Campaign → 多代候选评估
→ 每代 Phase 7 学习 → 全部代完成后统一 Phase 8 → 最终报告
```

两条链复用同一批领域能力（场景、策略、Lua、CMO、评估），但生命周期不同：

| 链路 | 适合的场景 | 状态真相 | 是否后台持续运行 |
| --- | --- | --- | --- |
| JSON→Lua | 用户调试一个场景、生成 Lua、按需执行 | `runs/<run_id>/` Artifact 与 `WorkflowState` | 否 |
| Training | 用户指定目标与代数，持续优化策略 | `runs/training/<workflow_id>/` + `runs/evolution/<campaign_id>/` | 是 |

### 2.1 主聊天 Agent 如何选择能力

正常入口是：

```powershell
python -m cmo_lua_agent.main chat
```

它默认使用 `all` profile，把普通工作区、JSON→Lua、数据库查询、单次 CMO、Training
和 Campaign 高层工具注册到同一个 `AgentLoop`。`standard`、`training`、`campaign`
仍可用于隔离调试，但它们只是缩小工具集合并给同一个 `MAIN_SYSTEM_PROMPT` 追加一段
范围说明，不是三套相互冲突的 Agent 或 Prompt。

仓库调查遵循：

```text
search_workspace 定位定义/调用
  → read_file 按行精读
  → 必要时继续搜索或读取
  → 得出结论或执行获批修改
```

所有通用文件工具共享 `WorkspacePathPolicy`：工作区外、`..`、符号链接以及任一组成
部分以点号开头的路径都会被拒绝。大型搜索或读取结果不会简单截断，而是完整写入
`runs/agent-artifacts/`，模型可再用 `read_file(start_line, end_line)` 分页读取。

### 2.2 上下文为何不是每轮固定裁成最近 12 条

`ContextManager` 会估算 system prompt、工具 Schema 和完整消息 JSON 的总 Token。当前
DeepSeek 默认窗口配置为 1,000,000 tokens：占用低于 80%（800,000）时原样发送完整
历史；达到阈值后才把请求副本压缩到约 60%（600,000）。聊天会话文件仍保存完整历史，
压缩摘要不会反向覆盖它。字符估算只用于提前判断阈值：ASCII 字符约按 0.3 token、
中文等非 ASCII 字符约按 0.6 token 计算并乘保守系数；每次端点返回的真实
`input_tokens` 会校准下一轮估算，因此系统没有把近似公式冒充精确 tokenizer。

## 3. 最重要的架构原则

### 3.1 LLM 是“受约束的决策组件”，不是执行器

所有真正使用 LLM 做判断的类集中在 `src/cmo_lua_agent/agents/`。例如：

- `strategy_intent_agent.py`：为四个候选方案生成意图；
- `strategy_patch_agent.py`：根据意图提出标量 Patch；
- `strategy_proposal_agent.py`：协调意图、Patch、角色约束和策略校验；
- `comparative_learning_agent.py`：比较多个候选方案，提出经验假设；
- `skill_author_agent.py`：把经过筛选的经验写成 Skill 草案；
- `lua_repair_agent.py`：对 CMO/Lua 故障提出结构化修复建议；
- `code_repair_agent.py`：复用现有模型客户端、`AgentLoop` 和六个受限工具，多轮定位并修复明确的 Python 系统故障；
- `system_repair_agent.py`：旧调用方式的兼容适配器，正式训练链已不再启动本地 Codex CLI。

LLM 不能直接：修改正式 Campaign 状态、绕过策略白名单、直接运行 CMO、直接写入 Experience/Skill 正式库，或把自由文本 Lua 当作可执行结果。

### 3.2 确定性代码维护“执行真相”

以下内容由 Python 确定性模块拥有：

- 场景和策略的类型/语义校验；
- JSON Patch 路径与对象 ID 校验；
- Lua 编译、渲染、预检；
- CMO 进程启动、日志解析和评分；
- Candidate 排名、Champion 选择、滚动基线；
- 状态机转换、文件原子写入、恢复、暂停和停止；
- 代码修复前的现场收集、源码快照、四步验证、原 action 重放、Git 提交与推送。

这样做的原因是：LLM 的输出天然不稳定，而“是否执行过、得到多少分、当前该重试还是完成”必须可以重放和审计。

### 3.3 状态落盘，不依赖聊天记忆

聊天记录只用于理解用户意图；训练是否完成、当前第几代、Worker 是否在运行，都不能由聊天上下文判断。

```text
Chat/CLI 负责：发起、查询、控制
TrainingStore/CampaignStore 负责：保存事实
TrainingRunner/CampaignService 负责：读取事实并推进下一步
```

这就是系统具备“Codex 式长期任务”能力的关键：即使终端关闭、后台进程重启，新的 Runtime 仍可读取状态继续工作。

## 4. 目录与模块地图

下面的表格可作为找代码时的导航图。

| 目录 | 核心职责 | 典型入口/类 | 面试应如何解释 |
| --- | --- | --- | --- |
| `agents/` | LLM 决策与结构化提案 | `StrategyProposalAgent`、`CodeRepairAgent` | 把不确定性集中到可替换 Agent，执行权不交给模型 |
| `training/` | 长期任务生命周期、异常路由、恢复与源码修复事务 | `TrainingService`、`TrainingRunner`、`TrainingStore`、`RecoveryRouter` | 类似任务调度器：请求、状态、Runner、后台进程和 Recovery Harness 分层 |
| `evolution/` | Campaign 控制平面和一代生命周期 | `ProductionEvolutionCampaignService`、`EvolutionCampaignService` | 训练领域的核心状态机，拥有 Campaign 真相 |
| `optimization/` | 候选策略装配、评估、比较与选择 | `OptimizationGenerationWorkflow`、`CandidateEvaluationWorkflow` | 负责“怎样形成并评估候选策略”，不负责长期调度 |
| `generation/` | StrategySpec→ExecutionPlan→Lua | Compiler、Renderer、Preflight | 可复现生成链，模型不直接生成最终 Lua |
| `execution/` | 启动 CMO、Job、日志、错误解析 | CMO Runner/Parser | 外部仿真程序的适配层与诊断层 |
| `evaluation/`、`scoring/` | 从正式结果提取评分与作战指标 | Phase 3 Evaluation | 评分来源受限，避免日志或猜测替代官方分数 |
| `learning/` | Phase 7 对比学习、经验存储、检索 | Learning Bundle、ExperienceStore | 从候选结果中提炼“带证据边界的假设” |
| `learning/skill_evolution/` | Phase 8 聚合、Skill 草案、回归、审批 | Skill Workflow | Skill 生命周期与训练执行分离 |
| `contract/` | 场景、策略、IR、Manifest 的类型契约 | Validators、Builders | 领域模型层，阻止脏数据进入下游 |
| `ingest/` | JSON 读入与基础画像 | `JsonLoader`、Profiler | 输入边界，尽早发现格式问题 |
| `integrations/cmolua/` | 外部 CMOLua/数据库适配 | Repository、Generator Adapter | 隔离外部依赖，业务层不直接依赖第三方细节 |
| `orchestration/` | 普通场景工作流、AgentLoop、会话状态 | `ScenarioWorkflow`、`AgentLoop` | 面向交互请求的编排，不承担 Campaign 真相 |
| `tools/` | 给 Agent 暴露的受控能力 | Tool Registry、Training Tools、Repair Tools | 普通聊天与源码修复使用不同 Registry，避免高权限工具串用 |
| `artifacts/` | 普通 Workflow 的运行产物写入 | `RunArtifactStore` | 统一文件布局和写入边界 |
| `cli/`、`bootstrap/`、`main.py` | 命令行和依赖组装 | `create_application`、`main` | Composition Root：只组装依赖，不写业务规则 |

## 5. 普通 JSON→Lua 工作流

### 5.1 调用顺序

```text
CLI/Chat Tool
  → bootstrap.create_application()
  → ScenarioWorkflow
      → JsonLoader
      → ScenarioSchemaValidator
      → ScenarioSemanticValidator
      → IRBuilder / IRValidator
      → DatabaseResolver
      → ManifestBuilder
      → LuaGenerationService
          → 外部 Generator Adapter
          → LuaPreflightValidator
  → RunArtifactStore
```

### 5.2 每一层做什么

1. **输入层**：读取用户 JSON，保证其是合法 JSON 对象。
2. **Schema/语义层**：分别回答“字段结构对不对”和“场景是否可执行”。两层分开使错误信息更准确。
3. **IR 与 Contract 层**：把原始 JSON 转换成稳定的领域对象，避免下游长期依赖松散字典。
4. **数据库解析层**：将用户名称、平台、武器等映射为 CMO 数据库中的可执行对象；不确定时要求用户确认，不能擅自猜 DBID。
5. **Manifest 层**：形成一次生成的输入清单，成为 Lua 与策略来源的可追溯证据。
6. **生成层**：基于确定性模板/渲染器生成 Lua，并执行预检。
7. **产物层**：把 Manifest、Lua、预检结果写入运行目录。

### 5.3 为什么不是“LLM 直接写 Lua”

直接生成 Lua 的问题是：难校验、难重现、难比较、难定位错误，也难保证它没有绕过计分或场景约束。

本项目将策略表达为 `StrategySpec`，再编译为 `ExecutionPlan`，最后渲染为 Lua。这样同一策略、同一 Runtime 和同一 Renderer 版本会产生可预期的产物；Lua 出问题时也能定位到策略、编译或渲染阶段。

## 6. 长期 Training Harness：最重要的一条链

### 6.1 用户视角

用户提供三样东西：

```text
ScenarioIR JSON 路径 + 优化目标 + 迭代代数
```

系统创建 Workflow 后立即返回 `workflow_id`；用户之后可以查询状态、暂停、恢复或停止，不需要逐代确认。

### 6.2 实际调用图

```text
TrainingService.start
  → ScenarioInputResolver.resolve
  → TrainingRequest.create
  → establish_training_baseline（仅提交并推送 src/、scripts/、tests/）
  → TrainingStore.create
      → last_good_commit 写入初始 state.json
  → TrainingProcessManager.start
  → training.runtime.run_workflow（后台进程）
  → TrainingRunner
  → ProductionCampaignDriver
  → ProductionEvolutionCampaignService
  → EvolutionCampaignService
  → ProductionGenerationExecutor
  → Candidate / CMO / Phase 7
  → 全部代完成后 Phase 8
  → TrainingReportWriter
```

### 6.3 Training 层的职责划分

#### `TrainingService`

面向 Chat/CLI 的门面，只负责：创建、查询、暂停、恢复、停止。它不直接跑多代循环，因此用户查询训练进度不会在前台阻塞。

创建 Workflow 前，`TrainingService.start()` 会先建立训练 Git 基线：自动暂存与提交范围严格限定为 `src/`、`scripts/`、`tests/`，随后执行 push，并把 SHA 写入初始 `last_good_commit`。基线 commit 或 push 失败时不会创建 Workflow，也不会启动后台进程。这样 Python 自动修复和对应回归测试拥有同一个恢复边界，同时不会把 `data/`、`runs/`、配置文件或其他工作区内容混入自动提交。

#### `TrainingStore`

保存一个 Workflow 的最小可恢复事实：

```text
runs/training/<workflow_id>/
  request.json       启动时冻结的用户请求
  state.json         Runner 的当前状态机真相
  journal.jsonl      诊断事件序列
  summary.json       给人快速查看的摘要
  TODO.md            当前阶段和下一动作提示
  runner.log         后台 Runtime 输出
  training-report.md 最终报告
  recovery-report.md 连续追加的恢复事故与验证结果（发生恢复时才存在）
```

关键点：`state.json` 才是恢复真相；`summary.json`、`TODO.md`、报告和日志只是辅助阅读，不能反向驱动状态机。`state.runner.recovery` 只保存当前事故的 action、代索引、尝试次数、最近路由和错误摘要，不创建另一套 Incident 状态目录；历史 state 缺少该字段时按空恢复状态读取。

#### `TrainingProcessManager` 与 `training.runtime`

前者只负责启动隐藏后台 Python 进程、保存 PID 和追加日志；后者在新进程中组装真实依赖、对账 Campaign，并循环调用 Runner。

PID 不是任务真相，只是健康检查线索。PID 丢失后仍能从 `TrainingStore` 恢复；这避免了“进程死亡 = 任务数据死亡”。

#### `TrainingRunner`

这是长期任务的持久化调度器。它根据 `TrainingState.action` 推进：

```text
PREVIEW → EXECUTE → SUMMARIZE/WAIT_WORKER → 下一代 PREVIEW
```

最终一代完成后才进入 Phase 8。Runner 不自己生成策略、不解析 CMO 日志、不重写 Campaign 算法；它只协调下一动作、等待、恢复和终态报告。

`run_once()` 捕获异常时不会立即把 Workflow 判为失败，而是先构造 `ErrorEnvelope`，再交给 `RecoveryRouter`：

```text
Exception
  → ErrorEnvelope（只记录事故事实）
  → RecoveryRouter
      → RETRY
      → DOMAIN_REPAIR
      → CODE_REPAIR
      → STOP
```

同一持久化 `stage/action/generation` 连续恢复失败最多三次。原 action 成功后会清空 `state.runner.recovery` 和退避信息；三次仍失败则停止 Workflow，但保留 `runs/`、CMO Artifact、日志和连续恢复报告。

### 6.4 为什么 Recovery Harness 不另建一套 Runtime

正式调用链仍然是：

```text
TrainingService → TrainingRunner → ProductionCampaignDriver → Campaign
```

Recovery Harness 只是 `TrainingRunner` 周围的错误现场、路由、上下文和验证能力，不是第二套调度器。没有新增 RuntimeSupervisor、恢复 DAG、向量数据库或新的运行状态目录。这样可以复用已有 Campaign 状态机和 Lua/Candidate Repair，避免两个 Runtime 同时决定“下一步做什么”。

### 6.5 为什么 Phase 8 放到全部代结束之后

Phase 7 的产物是每一代的经验提案；Phase 8 则聚合本 Workflow 的经验并形成 Skill 资产。

将 Phase 8 延迟到最后的好处：

- 当前训练过程中看到的经验集合保持稳定，不会“刚聚合出 Skill 又影响同一轮训练”；
- 聚合只执行一次，避免重复工作与重复晋升；
- 最终报告可清楚说明：本次训练产生了哪些经验、最终聚合了什么。

## 7. Campaign 与单代优化

Training 不是直接调用 CMO；它把“一代如何做”交给 Campaign 层。

```text
Campaign Prepare
  → 冻结输入包、场景、基线策略、运行时契约和知识快照
  → Preview：生成并冻结候选策略集
  → Execute：运行候选方案
  → Evaluate：正式评分与语义校验
  → Compare/Rank：比较候选方案
  → Champion：选择本代冠军
  → Phase 7：比较学习
```

### 7.1 `ProductionEvolutionCampaignService`

它是生产 Campaign 的**公开门面**。Chat Campaign 工具、Training Driver 和手工脚本都应该只调用它的公开方法，不能直接访问内部 `_services`、Store 或私有构建函数。

这样做的好处是：未来修改内部 Campaign 实现时，不会让多条入口各自复制状态机逻辑。

### 7.2 `EvolutionCampaignService` 与 `CampaignStore`

`EvolutionCampaignService` 是内部持久化控制引擎；`CampaignStore` 负责保存 Campaign 规格、预览、Worker 状态、操作账本和结果。

它们解决的核心问题是幂等和恢复：同一个已冻结预览不能因为重复查询再次消耗策略 LLM 调用；已经启动但结果未知的 CMO Attempt 不能在恢复时盲目重复执行。

### 7.3 Preview 为什么要冻结

Preview 阶段会：读取本代输入、生成候选策略、校验策略、记录候选集合和相关上下文。

之后 Execute 只消费冻结候选集，不应再次调用策略提案 LLM。原因是执行输入必须可重现：若点击“执行”时又生成一套新策略，用户就无法知道究竟评估的是哪一套候选方案。

## 8. 策略候选如何产生

### 8.1 两阶段策略提案

正式提案协调器是 `agents/strategy_proposal_agent.py`：

```text
冻结 Baseline + 场景 + 可修改路径 + 知识快照
  → StrategyIntentAgent：给四个固定候选角色生成意图
  → StrategyPatchAgent：为每个意图生成受限标量 Patch
  → StrategyPatchAssembler：从基线确定性装配 StrategySpec
  → StrategyValidator / Conformance Validator：校验
  → FrozenCandidateSet
```

四个候选角色体现“利用、稳健修复、协调探索、保守对照”等不同搜索方向。角色约束由系统拥有，LLM 只在允许的维度内表达目标与偏好。

### 8.2 为什么只允许标量 Patch

`StrategyChangeGuard`、Patch Catalog 和 Validator 共同限制模型：

- 只能修改白名单路径；
- 只能替换已有标量，不允许整体替换数组或对象；
- 必须匹配稳定对象 ID，防止数组重排后改错对象；
- 不能改场景 ID、平台/武器 DBID 等不可变事实。

这把模型输出从“任意程序”缩小成“可验证的小范围参数调整”，既便于探索，也避免破坏场景结构。

## 9. CMO 执行、评估与评分

### 9.1 执行层

`execution/` 负责把已冻结的 Lua 和 Job 配置交给 CMO 批处理程序，并持续解析日志和结果文件。它是外部进程适配层，不负责决定策略优劣。

### 9.2 评分层

正式评分必须来自指定的原生结果位置（如 `execution-summary.json` 中的官方最终分数）。日志文本、SQLite、CSV 或模型解释可用于诊断，但不能替代正式分数。

这条规则防止了一个常见问题：某个辅助指标看起来更高，但并不代表 CMO 的最终官方得分更高。

### 9.3 Candidate 结果的拆分

候选方案通常同时保存：

```text
execution_success  是否成功执行
scoreable          是否可获得正式评分
semantic_valid     是否满足策略/语义约束
official_score     官方最终分数
rank               是否可以进入排行
```

“有分数”不等于“可排名”。例如某候选方案即使执行完成并有分数，若语义校验失败，也不能作为 Champion；保留这两类事实有助于分析系统问题而不篡改原始仿真结果。

## 10. Phase 7：比较学习与经验

Phase 7 不重新运行 CMO，也不修改本代排名。它读取确定性组装的 `GenerationLearningBundle`，将多个候选方案的已知事实交给 `ComparativeLearningAgent`。

Agent 输出的是带证据态度的经验假设：

```text
support     支持某个可检验假设
contradict  与某个假设相矛盾
qualify     只能在特定条件下成立
```

经验不是“模型说得对就入库”。它仍要经过结构校验、证据边界处理和持久化流程。设计目标是防止模型虚构导弹数量、具体毁伤原因等输入不存在的事实。

## 11. Phase 8：Skill 聚合与生命周期

Phase 8 发生在一个 Training Workflow 的所有代完成之后：

```text
本 Workflow 的 Experience 集合
  → 聚合与资格筛选
  → SkillAuthorAgent 生成 Markdown 草案
  → 静态/可追溯/提案回归检查
  → Pending Skill
  → 人工审批后才成为 Active Curated Skill
```

这里的关键设计是：**训练自动化不等于自动把所有经验升级为正式知识。**

系统可以自动生成候选 Skill 和报告，但正式激活仍保留审核边界；这样可以避免一次异常训练把低质量结论长期污染知识库。

## 12. Recovery Harness：先路由，再恢复

### 12.1 `ErrorEnvelope`：统一错误现场

`ErrorEnvelope` 由 `TrainingRunner` 在异常边界构造，记录：`workflow_id`、当前 stage/action、generation、子任务、异常类型、消息、traceback、相关日志路径和相关源码。它只描述“发生了什么”，不保存模型猜测的根因、置信度或复杂指纹。

精简事故信息追加到 `journal.jsonl`，当前恢复进度写入 `state.runner.recovery`。完整 CMO 输出和业务 Artifact 仍保存在原目录，Recovery Harness 不复制另一份业务真相。

### 12.2 `RecoveryRouter`：四类错误、四种动作

| 类别 | 典型情况 | 动作 | 设计边界 |
| --- | --- | --- | --- |
| `TRANSIENT` | 超时、429/502/503、连接重置、Worker 临时文件竞争、CMO 临时占用 | `RETRY` | action 与代索引保持不变，使用已有指数退避 |
| `DOMAIN` | Lua、CMO、Candidate、StrategySpec 或评分语义失败 | `DOMAIN_REPAIR` | 只进入 Campaign/LuaRepairAgent/Candidate Repair，不修改 Python |
| `CODE` | ImportError、AttributeError、TypeError、兼容性或系统路径代码故障 | `CODE_REPAIR` | 进入 `CodeRepairCoordinator` |
| `UNKNOWN` | 固定规则无法可靠判断 | 一次 LLM JSON 诊断 | 输出仅允许四种动作；诊断端点失败或输出非法时按临时错误重试 |

固定规则优先于 LLM。只有 `UNKNOWN` 才调用一次现有 JSON 模型端点，这既保留了 Agent 对陌生错误的适应能力，也避免网络错误或明显 Python 异常每次都消耗一次诊断请求。

### 12.3 Lua/CMO 领域修复不能降级成 Python 修复

```text
DOMAIN_REPAIR
  → Campaign 已有 Preview 再生 / Candidate Repair / LuaRepairAgent
  → 重新渲染、校验或执行原领域动作
```

这条链修的是候选策略、Lua 或受登记的 Runtime Patch。若当前 Driver 没有可调用的领域修复入口，Runner 会停止并写报告，绝不会为了“让流程继续”而让 `CodeRepairAgent` 修改 Python 源码。这个边界避免业务结果不好被误判为系统代码 Bug。

### 12.4 `RepairContextBuilder`：给源码修复提供有限而完整的上下文

进入 `CODE_REPAIR` 后，上下文构建器收集：

- 原始训练任务和当前 `TrainingState`；
- `ErrorEnvelope`、traceback、`runner.log` 与相关日志摘要；
- 已存在的相关源码，不扫描或复制整个仓库；
- 当前 Git HEAD 与 `last_good_commit`；
- `data/recovery/known-issues.md` 的有限内容；
- 最小修改、不改变评分/场景语义、不删除 Artifact、保持接口兼容、由 Harness 提交 Git 的约束。

这样 `CodeRepairAgent` 能理解事故现场，但不能自行扩大修复目标。模型负责提出并执行最小源码修改，Harness 继续拥有验证、回滚、提交和状态推进权。

### 12.5 `CodeRepairAgent`：自研的工具调用修复循环

正式修复内核不调用本地 Codex CLI。`training/runtime.py` 把当前配置的 `ClaudeClient` 注入 `CodeRepairAgent`，Agent 再复用普通系统已有的 `AgentLoop`、`ContextManager`、`ToolRegistry` 和 `AgentEvent`：

```text
CodeRepairAgent
  → ContextManager 构造有界上下文
  → 模型选择 Repair Tool
  → ToolResult 返回可观察结果
  → 模型根据结果继续读取、修改或测试
  → RepairAgentResult(COMPLETED/FAILED/TIMED_OUT/CANCELLED)
```

Code Repair 策略没有固定工具轮数上限，但一次尝试最多运行 30 分钟。它移除了普通 CMO 聊天中的“连续读取属于无效轮次”等启发式判断，因为源码诊断本来就可能需要反复搜索和阅读。完整消息仍保留在当前进程内；每次请求模型前由 `ContextManager` 压缩成有界上下文，Runtime 重启时不恢复旧 Agent 对话，而是从持久化事故现场重新修复。

专用 Registry 只注册六个工具：

| 工具 | 作用 | 关键约束 |
| --- | --- | --- |
| `search_code` | 在代码范围内搜索文本 | 只搜索 `src/scripts/tests` |
| `read_repair_file` | 分段读取源码或本次诊断 Artifact | Artifact 只读，不能借此扩大写权限 |
| `edit_repair_file` | 精确替换已有文本 | `old_text` 必须恰好匹配一次 |
| `create_repair_file` | 新建源码或回归测试 | 禁止覆盖已有文件 |
| `run_repair_command` | 运行 pytest/compileall | `argv` 列表、`shell=False`、独立超时 |
| `inspect_repair_diff` | 只读查看改动 | 不允许 add、commit、reset 或 push |

所有写入路径在 `resolve()` 后必须仍位于 `src/`、`scripts/` 或 `tests/`，并拒绝绝对路径、`..` 和符号链接逃逸。Agent 不能执行 Git、控制 CMO/Campaign/Workflow、直接修改状态文件，也不能删除 `data/`、`runs/` 或仿真 Artifact。这不是让模型“拥有终端”，而是给它一组足以完成源码诊断、但副作用边界明确的能力。

搜索、pytest、compileall 或 diff 结果过大时，完整内容写入当前 Workflow 的 `repair-artifacts/`，模型先收到摘要和仓库相对路径，随后可用 `read_repair_file` 分页读取。因此上下文压缩不会把关键诊断日志永久丢掉，这些文件也不承担状态真相。

### 12.6 `VerificationGate` 与失败 action 恢复

Agent 返回 `COMPLETED` 后，外层门禁依次执行：

```text
1. git diff --check -- src scripts tests
2. 调用方传入的针对性测试
3. 按改动顶层包匹配的回归测试；没有对应目录则跑完整测试集
```

Agent 内部运行的测试只用于诊断，不能代替外部门禁。Gate 成功后，`TrainingRunner` 才调用 `CampaignDriver.reconcile()`，读取当前代 Preview、Worker、Operation 和 Result Artifact，恢复原失败 action 的最小未完成步骤：已有 Preview 或结果会直接复用；运行中的 Worker 只进入等待；`WAIT_WORKER/SUMMARIZE` 只检查状态；无法证明 CMO 是否启动过时停止并报告，绝不冒险重复启动。

因此这里不是简单调用 `_run_once()` 或重放整个 Generation。测试验证一般代码行为，reconcile/resume 验证当前 Workflow 现场真的能继续，并同时保护既有 Artifact 不被覆盖。

### 12.7 `CodeRepairCoordinator`：源码修复事务与中断恢复

```text
CODE_REPAIR
  → 原子快照 src/、scripts/、tests/ 并记录训练前脏文件
  → CodeRepairAgent 多轮搜索、读取、修改和测试
  → VerificationGate
  → Campaign reconcile/resume 原失败 action
  → 失败：恢复本次快照，不提交
  → 成功：只提交本次 src/、scripts/、tests/ 改动
  → git push
      → 成功：更新 last_good_commit，继续训练
      → 失败：保留本地已验证 commit，写报告并停止 Workflow
```

`state.runner.recovery.status` 使用 `IDLE → REPAIRING → VERIFYING → COMMITTED → IDLE` 表示可恢复事实。若 Runtime 在 `REPAIRING/VERIFYING` 中断，下一次启动恢复持久化 zip 快照、增加尝试次数，再根据同一个 `ErrorEnvelope` 发起全新的 Agent 修复，不恢复旧对话；同一 action 三次失败后进入 `FAILED/STOPPED`。若本地 commit 已完成但 push 未完成，只在 HEAD 等于已记录 commit 时重试 push，避免重复修复和提交。

修复失败后 Runner 不会使用 `git reset --hard` 覆盖用户未提交文件。若 reconcile 已经产生新业务 Artifact、随后 commit 失败，则保留已验证源码和 Artifact 并停止，避免把源码恢复到与新 Artifact 不兼容的旧版本。连续事故统一追加到 `recovery-report.md`，记录错误、路由、动作、修改文件、验证、commit/push 和结果；旧 `code-repair-report.md` 可以继续保留，但新流程不再生成它。

### 12.8 轻量恢复经验

首次成功的 CODE/UNKNOWN 源码修复只有在验证、原 action 重放、commit 和 push 全部成功后，才会把症状、根因摘要、恢复动作、修改文件、验证方式和 commit 追加到 `data/recovery/known-issues.md`。相同事故不会重复追加。

它只是下一次诊断的有限参考文本，不是新的状态数据库，也没有引入 Embedding、向量检索或诊断 Agent。面试时可以把它概括为“用最小成本积累已验证恢复经验”。

## 13. AgentLoop 与 TrainingRunner 的区别

两者都像“循环”，但职责完全不同：

| 组件 | 解决的问题 | 真相来源 | 何时结束 |
| --- | --- | --- | --- |
| `AgentLoop` | 一次聊天请求中如何调用工具、组织对话 | 当前会话与工具返回 | 模型给出最终回答或需要用户信息 |
| `TrainingRunner` | 长时间多代训练如何推进和恢复 | `TrainingStore`、Campaign Artifact | 完成指定代数、停止、失败或等待人工 |

不要把 AgentLoop 当作多小时训练的调度器。训练不应受“单次请求调用了多少轮工具”限制；它应该由持久化状态、用户指定代数和显式控制操作决定。

## 14. 常见面试问题与回答模板

### Q1：为什么要把 Agent 放在 `agents/`，而不是散落在业务模块里？

答：为了把不确定性的 LLM 决策面集中起来。业务模块保留确定性校验、执行和持久化；当我需要替换模型、调整 Prompt 或审计模型决策时，可以先定位 `agents/`，不会在多个业务文件里寻找隐藏模型调用。

### Q2：系统如何保证训练断了还能恢复？

答：请求、状态、事件和 Campaign 产物全部落盘。`TrainingRunner` 每次只推进一个持久化 action，后台进程重启后重新加载 `state.json` 和 Campaign 状态继续，不使用聊天历史或旧进程内存判断进度。异常恢复次数和最近路由保存在 `state.runner.recovery`，因此进程重启也不会丢失当前事故边界。

### Q3：为什么需要 Preview 和 Frozen Candidate Set？

答：Preview 将“模型提出候选方案”与“执行候选方案”分离。候选一旦冻结，Execute 不再重新调用 LLM，保证实验输入可追溯、可重复，避免重复点击执行导致不同策略混入同一代。

### Q4：为什么 LLM 不能直接生成 Lua？

答：Lua 是可执行产物，直接生成难以约束。系统让模型输出受限 `StrategySpec` 或 Patch，再经确定性编译、渲染和预检生成 Lua，保证可验证、可重现，也便于定位错误。

### Q5：如何防止训练中的自动修复破坏用户代码？

答：训练启动前先建立只包含 `src/`、`scripts/`、`tests/` 的 Git 基线；代码修复协调器再原子保存同范围快照和已有脏文件。Agent 只能使用六个受限工具，不能执行 Git、CMO 或 Workflow 控制。修复必须通过差异检查、针对性测试、受影响包回归和失败 action 的 reconcile/resume，失败就恢复本次快照。成功后由外层 Harness 提交并 push；push 失败保留本地验证 commit 但停止训练。整个过程不使用 `git reset --hard`。

### Q6：Phase 7 和 Phase 8 有什么区别？

答：Phase 7 是每代后的对比学习，生成带证据边界的经验；Phase 8 是所有代结束后的经验聚合与 Skill 生命周期处理。分开可以避免聚合中的新知识反过来污染同一轮训练。

### Q7：为什么不把所有异常都交给 CodeRepairAgent 修改源码？

答：因为失败原因属于不同责任域。网络超时应该重试；Lua、CMO 和候选策略失败应该进入领域修复；只有明确的 Python 系统故障才允许修改源码。如果把业务评分差、Lua 语义错误或端点 502 都当作 Python Bug，系统会用代码修改掩盖真实问题。`RecoveryRouter` 的价值就是先守住责任边界，再选择恢复动作。

### Q8：自动修复已经跑过测试，为什么还要重放原 action？

答：测试验证的是一般代码行为，失败 action 恢复验证的是当前 Workflow、Campaign 和持久化状态是否真的恢复。Runner 不会粗暴重跑整个 Generation，而是先 reconcile Artifact，再恢复最小未完成步骤。只有该步骤成功，Runner 才能安全推进。因此 reconcile/resume 是 commit 前的业务恢复门，不是普通单元测试的重复。

## 15. 推荐的学习顺序

如果你要真正读懂代码，建议按下面顺序，不要从 200 多个文件随机开始：

1. `docs/architecture/runtime-entrypoints.md`：先确认唯一正式入口。
2. `training/service.py`、`training/store.py`：理解请求、Git 基线和最小持久化状态如何建立。
3. `training/runner.py`：理解 action 状态机以及正常推进和异常恢复如何汇合。
4. `training/recovery.py`：理解 `ErrorEnvelope`、四类路由、修复上下文、验证门和轻量恢复经验。
5. `agents/code_repair_agent.py`、`tools/repair_tools.py`：理解自研工具调用修复循环和模型权限边界。
6. `training/repair.py`：理解持久化快照、验证、reconcile、回滚、提交和中断恢复事务。
7. `training/runtime.py`：理解后台进程如何把当前 LLM Client 注入 CodeRepairAgent，并组装真实 Campaign 和 UNKNOWN JSON 诊断器。
8. `evolution/production_service.py`、`evolution/control_plane.py`：理解 Campaign 门面和控制引擎。
9. `evolution/production_executor.py`：理解一代是如何被执行的。
10. `agents/strategy_proposal_agent.py`、`strategy_intent_agent.py`、`strategy_patch_agent.py`：理解模型如何受约束地产生策略。
11. `optimization/` 与 `generation/`：理解策略如何变成 Lua 并被评估。
12. `learning/` 和 `learning/skill_evolution/`：最后理解经验与 Skill 如何沉淀。

## 16. 最后可复述的项目总结

你可以在面试中这样概括：

> 我把系统设计成“LLM 负责有限决策，确定性流程负责执行真相”的分层架构。用户可以通过一句话启动多代 CMO 策略训练，后台 Runner 根据持久化状态推进 Campaign；每代先冻结候选策略，再运行 CMO、评估和比较，完成后沉淀经验，所有代结束后统一聚合为 Skill。训练启动前建立限定于 `src/`、`scripts/`、`tests/` 的 Git 基线；运行异常先封装为 `ErrorEnvelope`，再路由为临时重试、领域修复、Python 源码修复或停止。Python 修复由自研 `CodeRepairAgent` 复用现有模型客户端和 `AgentLoop`，通过六个受限工具多轮搜索、读取、精确编辑和测试；Git、Workflow 与 CMO 控制仍由外层 Harness 掌握。源码和回归测试必须经过差异检查、针对性测试、包级回归和 Campaign reconcile/resume，全部成功才 commit/push 并继续训练。这样获得了 Codex/Claude Code 风格的自适应修复能力，又保留 Campaign、仿真、评分和状态机的可复现性。
